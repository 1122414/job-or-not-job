# 静态光照输入与活场景分离

## 信号与机制

给建筑标记Static后直接`VoxelGI.bake(game)`，不能保证只烘焙建筑。GeometryInstance3D默认GI模式本来就是Static；活场景内人物、道具和交互附件也可能被遍历。2026-09-30本项目实测826个可见人物/可动物件网格为Static，这是全场景候选数，不能等同于四个体积内的最终烘焙数。

另一独立输入问题：Godot4.7 VoxelGI通过MultiMesh的get_meshes路径收集底层网格，烘焙器路径没有像MeshInstance3D那样带入实例材质覆盖。世界三平面纹理也不能按可见材质效果直接假定会被正确烘焙。

## 处理与验证

`tools/city_lighting_bake.gd`只提取四处房间和地基，明确跳过面试手机/纸张/盒子、翻页图册、窗帘；人物和可移动家具的父节点不在范围中。MultiMesh展开为MeshInstance3D，显式解析覆盖材质。仅烘焙代理将三平面纹理变为线性空间计算的低频平均色，不改运行时材质；透明面不当作实体遮挡，不支持的材料拒绝制作。

`tests/city_lighting_bake_test.gd`在真实场景比较2089个代理：改变人物、物件、翻页、窗帘、灯开关后输入不变；改变固定沙发位置后输入改变。另检查实例覆盖优先级、平均色与原材料保持。验证一次。四份实际GPU资源经独立进程加载，11张图逐字节一致；错误源码/资源摘要拒绝。见`docs/2026-09-30_C4l2a静态光照制作管线验收.md`及其证据目录。

## 边界

该方法只证明输入与制作/加载一致，不证明最终画质。它没有解决动态遮挡、探针过渡、自然昼夜刷新或长期内存。不得将排除动态网格解释为所有活动人物都不受GI照明；接收光照与贡献烘焙是不同职责。新场所、会移动的家具或新材质必须重新审查，不能直接扩大白名单遍历范围。
